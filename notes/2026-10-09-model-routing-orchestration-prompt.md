## 投稿の主張

- GPT-6 Astra にこのプロンプトを渡すと、dots が Astra ultra でいくら作業しても「トークンが全く減らなくなる」。
- **→ 誇張。** 実際の仕組みは「簡単な作業は安いモデル・低い推論レベルに振り分ける」こと。消費は減るが、ゼロにはならない。
  - 判定役の Jev(TypeSafe)自体も有料API。報告ベースで入力100万トークンあたり$0.042。
  - 直接APIはウェイトリスト制。OpenRouter 経由でも使える。

## プロンプトの構成(要約)

| セクション | 内容 |
| --- | --- |
| オーケストレーション | 自分は設計・指揮役。「必要最小限のモデルと推論レベル」で確実に仕上げる |
| Jev | 外部の分類器(`TYPESAFE_API_KEY`)を、判断だけに使う。対象は難易度の分類、レーン選択、継続か停止か、リトライ、エスカレーション、完了判定。コードを書くこと・設計・汎用推論・ツールで答えが出る質問には使わない。毎回のツール呼び出し後には呼ばない |
| 初期ルーティング | SMALL / MEDIUM / HIGH は Luna の low / medium / high、ESCALATE は Sol の high。常に「足りる中で一番軽いレーン」から始める |
| エージェントループ | 判断の区切りごとに、①実際の差分を確認 → ②決定論的な検証を実行 → ③証拠を集める → ④迷えば Jev に聞く → ⑤ CONTINUE / RETRY / VERIFY / ESCALATE / COMPLETE から1つ選ぶ。Jev には最小限の文脈だけ送る |
| エスカレーション | 証拠があるときだけ上げる。例: 実装の失敗が続く、テストやビルドが落ち続ける、影響範囲が想定より大きい、セキュリティ・移行・データ消失のリスク。「強いモデルがあるから」は理由にならない |
| 高リスク変更 | 認証・認可・決済・移行・データ削除・並行処理・暗号・大きな設計変更は、完了前に必ず最上位モデルでレビューする |
| 決定論的な検証 | AIの判断より、テスト / コンパイル / 型 / lint / ビルド / フォーマッタ / git diff を優先する |
| 完了条件 | 要求が実装済み、検証が通過、差分が依頼の範囲内、未解決の失敗なし、必要なレビューが通過。**失敗を隠さない。実行していない検証を「実行した」と言わない** |

## 使える原則(モデル・サービスに関係なく使える)

1. **安いモデルから始め、証拠があるときだけ上げる。**
   - Claude Code なら、軽い調査はサブエージェントを Haiku や Sonnet に、難所だけ上位モデルにする。
   - 推論の深さ(effort)も同じ考え方で調整する。
2. **AIの「たぶん大丈夫」より、テスト・ビルド・lint の結果を信じる。**
3. **完了の定義を先に決めておく。** 特に「実行していない検証を報告しない」は、どのエージェントでも必須。
4. **高リスクな変更(課金・認証・データ削除)だけは、別の目でレビューする。**

## このアプリ(競馬アプリ)での活かし方

- アプリ本体のリポジトリの `CLAUDE.md` に、上の原則を短く書いておく。例:
  - 完了前に `xcodebuild test` と SwiftLint を実行する。
  - 課金(StoreKit)・ATT・個人情報まわりの変更は、必ず人がレビューする。
- 課金・プライバシーに関わる変更は「高リスク」扱いにする。プライバシーポリシー(このリポジトリ)の更新が必要かも確認する。

## 注意点

- Jev / TypeSafe を使うと、判断に必要な文脈(コードの断片など)が**外部サービスに送られる**。非公開コードを扱うなら規約を確認する。
- API キーは環境変数で管理し、ログやコミットに出さない(プロンプト自体もそう指示している)。
- 「トークンが減らない」系の煽り文句は、仕組みを確認してから使う。
